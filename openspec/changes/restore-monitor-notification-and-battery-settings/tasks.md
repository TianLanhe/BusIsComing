## 1. 先建立失敗測試

- [ ] 1.1 為通知總開關、狀態渠道、提醒渠道及鎖屏可見性的健康狀態判定補充失敗單元測試
- [ ] 1.2 為渠道設定、App 通知設定、App 詳情與手動指引的逐級回退補充失敗單元測試
- [ ] 1.3 為監控啟動順序、待恢復啟動狀態及每次嘗試只提示一次補充失敗單元測試
- [ ] 1.4 為電池最佳化豁免狀態、直接請求與不可用回退補充失敗單元測試

## 2. 實作通知渠道檢查與設定跳轉

- [ ] 2.1 抽取通知渠道管理元件，集中建立渠道並讀取 App 通知及兩個監控渠道的實際狀態
- [ ] 2.2 實作可測試的渠道健康判定，區分阻斷、警告、就緒與無法判定狀態
- [ ] 2.3 實作可測試的通知設定導航器，依次回退至渠道設定、App 通知設定、App 詳情及手動指引
- [ ] 2.4 讓前台服務與啟動流程共用渠道管理元件，避免重複或不一致的渠道建立邏輯

## 3. 接入監控啟動面板與返回重檢

- [ ] 3.1 在監控啟動面板加入通知準備狀態、修復按鈕與無障礙描述
- [ ] 3.2 在啟動監控前處理阻斷、警告與無法判定狀態，僅阻斷狀態暫停啟動
- [ ] 3.3 保存待恢復的監控啟動資料，從系統設定返回後重新檢查並只在問題已修復時繼續
- [ ] 3.4 為無法跳轉或無法可靠判定的裝置提供繁中、簡中及英文手動操作指引

## 4. 恢復直接請求電池最佳化豁免

- [ ] 4.1 恢復 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 權限與豁免狀態檢查
- [ ] 4.2 恢復帶 App package URI 的系統豁免確認頁，並在 Intent 不可用或啟動失敗時降級繼續
- [ ] 4.3 按通知渠道、精確鬧鐘、電池豁免、前台服務的順序編排監控啟動流程
- [ ] 4.4 確保拒絕豁免不阻斷當次監控，且同一次啟動嘗試不重複彈出豁免請求
- [ ] 4.5 補齊繁中、簡中及英文的用途、耗電影響、設定狀態與失敗提示文案

## 5. 驗證與交付

- [ ] 5.1 運行新增及相關單元測試，確認測試先失敗後因實作通過
- [ ] 5.2 運行 OpenSpec 嚴格校驗並檢查變更與任務一致性
- [ ] 5.3 運行 `./gradlew build`
- [ ] 5.4 在本任務新啟動的模擬器或可用測試裝置上驗證渠道阻斷、警告、返回重檢及電池豁免流程；若沒有可用裝置則明確記錄未完成的手動驗證
- [ ] 5.5 檢查工作區與提交範圍，依專案規則提交實作改動
