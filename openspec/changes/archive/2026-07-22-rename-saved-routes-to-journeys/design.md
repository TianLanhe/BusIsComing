## Context

BusIsComing 目前存在兩個被同稱為「路線」的產品概念：`RouteConfig` 保存的是用戶可重複使用的名稱、起點和終點，例如「上班」或「回家」；`BusRouteOption` 則表示 Citybus 點到點查詢返回的乘車方案，例如 `118` 或 `85 → 106`。前者不綁定後者，同一個保存配置每次查詢都可返回多條不同方案。

英文 runtime 文案已大致把保存配置稱為 `Regular journey / journey`，繁體與簡體仍大量使用「常用路線／常用路线」，令三語的概念邊界不一致。受影響文案分散於常用首頁、首次引導、行程表單與管理、搜尋保存、設定、匯入匯出、Dialog、Toast 和無障礙描述；查詢結果、路線卡、ETA、路線詳情及通知監控又必須繼續使用「路線」。因此不能以全域字詞替換完成。

這次變更只調整用戶可見文字和現行文件。現有 Kotlin 模型、resource key、SQLite schema、`.bicroutes` 協議、查詢資料流及外部服務均已穩定，為術語純度重命名它們會帶來大範圍低收益改動。

## Goals / Non-Goals

**Goals:**

- 建立「行程 → 查詢 → 多條路線 → 一個或多個乘車段」的清楚產品概念。
- 讓繁體、簡體和英文的 App 自有文案使用一致且自然的術語。
- 完整覆蓋保存配置的建立、管理、選擇、保存、匯入匯出、狀態提示及無障礙內容。
- 保留查詢結果及 Citybus 巴士服務的「路線」語義，避免誤改。
- 在本地化指南、項目級 agent 規則和現行產品說明中沉澱可持續執行的術語規則。
- 以自動化測試、完整構建及必要的三語版面檢查確認只改文字、不改行為。

**Non-Goals:**

- 不重命名 `RouteConfig`、repository、Activity、Adapter、函式、變數、檔名或套件。
- 不重命名 Android string resource key，也不新增術語轉換抽象。
- 不修改 SQLite 表／欄位／schema version、已保存資料、`.bicroutes` 副檔名或 JSON schema。
- 不改變行程新增、編輯、複製、刪除、排序、查詢、保存、匯入匯出或通知監控流程。
- 不修改 Citybus、DATA.GOV.HK、Google 請求、解析、cache、語言 snapshot、callback 或第三方原文。
- 不批量重寫已完成或歷史 OpenSpec change artifacts。

## Decisions

### 1. 以三層術語模型作為唯一產品語義

保存並可重複使用的名稱、起點和終點稱為「常用行程／行程」；查詢返回的一個直達或換乘方案稱為「路線」；路線中的單段巴士服務稱為「乘車段」。繁體、簡體和英文對應如下：

| 語義 | 繁體中文 | 簡體中文 | English |
| --- | --- | --- | --- |
| 保存的起終點配置 | 常用行程／行程 | 常用行程／行程 | Regular journey / journey |
| 查詢返回的乘車方案 | 路線 | 路线 | Route |
| 方案中的單段巴士服務 | 乘車段 | 乘车段 | Leg |

頁面標題、首次引導及脫離上下文的位置使用「常用行程」，語境已清楚的欄位和操作可使用「行程」。`乘車段` 只在路線詳情或換乘結構需要時使用，不新增到一般查詢頁造成額外認知負擔。

**理由：**「上班」描述用戶的出行意圖，而 `118` 描述其中一個可選方案；兩者具有穩定的一對多關係。英文目前已採用 journey，這個模型亦能自然對齊三語。

**否決方案：**繼續使用「常用路線／查詢路線」只依賴上下文區分，無法消除同頁選擇配置與展示結果時的歧義；把查詢結果改稱「方案」則會偏離香港巴士用戶熟悉的「路線」用語，並影響大量已穩定的結果文案。

### 2. 按 resource 語義逐項審查，不做全域替換

實作時先以 `rg` 掃描三個 locale 的 string resources，以及 XML／Kotlin 中可能存在的硬編碼文字，再把每個命中分為兩類：

- **行程類：**常用區塊、首次引導、新增／編輯／複製／刪除／管理、行程名稱、保存為常用、行程資料、匯入匯出、已保存數量、錯誤／成功提示及對應無障礙描述。
- **路線類：**查詢路線、查詢結果數量、路線卡、路線號、排序、票價、耗時、步行距離、ETA、路線詳情、站點、方向及換乘方案。

只修改第一類的 resource value，保留 resource key。對同時包含兩個概念的句子按整句重寫，例如表達「選擇常用行程後查詢路線」，不得以機械替換產生「查詢行程」等錯誤文案。繁體使用香港實用書面語，簡體獨立審校，英文不因中文調整而逐字翻譯。

**理由：**兩類文案共用 `route` 前綴，按 key 名或中文字面批量替換容易破壞正確的查詢路線語義。

**否決方案：**重命名所有 string resource key 可令內部命名更純粹，但會觸及大量 XML、Kotlin 和測試引用，超出「只改界面文案」的明確範圍。

### 3. 內部符號與持久化協議保持兼容

`RouteConfig`、`RouteConfigRepository`、`selectedRoute` 等既有內部命名繼續使用；SQLite `route_configs`、所有欄位與 schema version 不變；`.bicroutes` 的副檔名、版本、JSON 欄位及匯入兼容不變。resource key 亦保持不變，僅更新不同 locale 的 value。

這次沒有新的資料流、線程、cache、取消或生命週期處理。UI 仍從 Android resources 取得文字，model／repository／service 仍返回原有結構化狀態，Citybus 查詢和增量 ETA 更新完全沿用現有流程。

**理由：**內部命名並不直接暴露給用戶，保留它們可以把風險限制在可審查的文字層，亦避免資料遷移或舊匯入文件不兼容。

**否決方案：**把 `RouteConfig` 全面改為 `SavedJourney` 雖然內外一致，但會牽涉資料層、UI state、測試、檔名和可能的序列化邊界，收益不足以支持本 change 的成本和風險。

### 4. 以本地化指南作為權威術語來源

`docs/localization-guidelines.md` 的三語術語表是 runtime 文案的權威來源；`AGENTS.md` 加入簡潔的長期概念規則並指向該指南；`README.md` 及描述目前產品行為的現行文件同步採用「行程／路線」。新 capability spec 提供可驗收的產品需求。

已完成或歷史 OpenSpec artifacts 記錄的是當時的決策，不進行批量回寫。它們出現的舊術語不再作為新 runtime 文案的基線；後續新 change 必須遵循本 change 與本地化指南。

**理由：**單一權威表可避免 README、設計文件和 runtime 各自演化；保留歷史 artifacts 則維持變更記錄的可追溯性。

**否決方案：**修改所有歷史 specs 和 changes 會造成龐大文件 diff，模糊真正的產品改動，也可能改寫已完成變更的原始驗收語境。

### 5. 以語義、構建和版面三層驗證完成度

驗證分為三層：

1. **語義掃描：**重新搜尋三語 resources、XML、Kotlin 和現行文件，逐項確認行程類舊文案已清理，同時抽查「查詢路線」「路線詳情」「路線號」等負向保留項。
2. **自動化驗證：**只更新直接斷言受影響文字的測試期望，運行相關 unit／instrumentation 測試，最後運行 `./gradlew build`。
3. **界面驗收：**覆蓋繁體、簡體、英文 × 淺／深色，以及約 360dp、font scale 1.0／1.3／2.0 的高風險畫面，檢查標題、按鈕、Dialog、Toast、匯入匯出摘要和 content description 不截斷且語義一致。

不需要外部 API cURL、fixture 或真實服務回歸，因為請求、解析、動態資料和語言 mapping 均不變。若當前沒有設備，交付時須明確記錄未完成的手動視覺驗證。

**理由：**純文案改動的主要風險是語義誤替換、漏改和版面長度，而不是資料或網路回歸；驗證資源應集中在這三類風險。

**否決方案：**只依賴 `./gradlew build` 無法發現錯誤用詞或大字體截斷；只做人工檢查則不能保證 resource 和測試完整性。

## Risks / Trade-offs

- **[把正確的查詢「路線」誤改為「行程」]** → 使用行程類／路線類清單逐項審查，並在完成掃描中加入必須保留的負向詞組。
- **[遺漏 Toast、Dialog、無障礙或匯入匯出長文案]** → 除 `strings.xml` 外同步搜尋 XML、Kotlin、測試及所有 locale，按畫面流程建立驗收清單。
- **[新文案長度造成窄屏或大字體截斷]** → 沿用可伸縮版面，在三語、360dp 和 font scale 1.0／1.3／2.0 下檢查高風險畫面；本 change 不以縮字解決問題。
- **[內部仍使用 RouteConfig 令開發者誤解]** → 在 `AGENTS.md` 和本地化指南明確說明內部歷史命名是兼容例外；後續 runtime 文案不得依內部符號直譯。
- **[歷史 OpenSpec 仍含舊詞造成看似矛盾]** → 明確把歷史 artifacts 視為當時記錄，新的 capability spec 與本地化指南作為後續文案準則，不批量回寫。
- **[只改文字但測試快照失敗]** → 僅更新直接受影響的期望字串，保留測試步驟、資料和行為斷言。

## Migration Plan

1. 盤點並分類三語 runtime 文案及直接斷言它們的測試。
2. 更新三語 resource value，保持 key 和所有 Kotlin 引用不變。
3. 更新本地化指南、`AGENTS.md`、`README.md` 及必要的現行產品文件。
4. 執行語義掃描、相關測試、完整構建和可用的模擬器／實機版面驗收。

此變更不包含資料遷移或分階段發布。若需要回退，只需回退文字與文件改動；SQLite、`.bicroutes` 和外部服務狀態不受影響。
