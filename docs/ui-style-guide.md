# BusIsComing UI 風格指南

## 風格定位

BusIsComing 的預設界面風格是：安靜實用的現代通勤工具。

這個風格優先服務每天反覆使用的路線查詢場景。界面應該清楚、輕快、可信賴，避免營銷化、裝飾化或後台表格化。後續通過 OpenSpec 新增或改造頁面時，預設採用本指南，除非對應 change 明確説明偏離原因。

## 設計原則

- 資訊優先：優先突出路線、候車時間、價格、總耗時和步行距離，不用裝飾元素搶佔注意力。
- 閲讀舒適：移動端字號以可讀為先，不為了一屏塞更多行而犧牲核心資訊可讀性。
- 層次清楚：主資訊大、深、靠前；輔助資訊小、淺、靠後；操作按鈕按主次分級。
- 輕量現代：使用卡片、狀態提示、圖示按鈕、淡入/滑入等輕量反饋提升現代感，但不做誇張動畫。
- 通勤語境：視覺語言應接近日常出行工具，而不是營銷落地頁、後台管理系統或純表格工具。
- 一致沉澱：新頁面、新組件、新互動應複用本指南里的顏色、圓角、間距、動效和資訊層級。

## 視覺語言

預設保留當前深青綠作為主色，琥珀色作為輔助操作色，並增加更清晰的中性色層次。

- 主色用於核心操作、關鍵狀態和選中態。
- 輔助色用於次級但需要明顯按鈕感的操作，例如管理入口或強調型快捷入口。
- 淺色模式使用淺色中性表面；深色模式使用深青綠夜行色系的深色頁面與分層 surface，不以純黑取代語意色。
- 卡片使用輕微描邊或淺陰影表達層次，不使用厚重邊框。
- 圓角保持克制，普通卡片建議 8dp 左右，主要操作按鈕可略大，但不要全域過度圓潤。
- 不使用漸變球、裝飾光斑、無意義插畫或大面積宣傳型 hero。

### 外觀模式與語意色

- 設定頁提供跟隨系統、淺色與深色三種模式；外觀與 App 語言是獨立偏好。
- layout、drawable 與 Kotlin 動態 View 應使用 `bus_*` 語意 token，不直接使用固定白色、黑色或日間 surface。
- 深色模式的主要文字對比至少 4.5:1，必要圖示與邊界至少 3:1；選中、停用、錯誤與 ripple 不能只靠明度差異辨識。
- launcher、品牌圖像與路線識別色可保持固定，但路線 badge 的前景必須在淺深主題都有足夠對比。
- status bar、navigation bar、Dialog、Bottom Sheet、TextInputLayout、Notification 與系統圖示明暗必須與目前主題一致。

### 多語言與大字體

- 核心 action 使用 `wrap_content + minHeight 48dp`，英文與 font scale 2.0 時允許換行或滾動。
- 不以縮字、固定單行或裁切核心方向、備註、狀態和按鈕容納翻譯。
- 快捷卡的用戶行程名或站名可作受控省略；詳情與 `contentDescription` 必須保留完整文字。
- 完整語言、動態資料、TTS 及驗收規則見 `docs/localization-guidelines.md`。

產品術語依本地化指南區分：用戶保存的名稱、起點和終點是「行程」，查詢返回的 `118` 或 `85 → 106` 等乘車方案是「路線」。內部 `RouteConfig` 等歷史命名不得直接用作 runtime 文案。

### 頂層底部導航

- 「常用／搜尋／設定」使用等寬 Material 底部導航項，切換 destination 不改變導航欄或頁面內容的量度。
- 目前 destination 持續顯示膠囊形 active indicator；點擊 ripple 只表示短暫按下，不得代替選中狀態。
- 圖示使用固定 `28dp` 槽位：選中圖示填滿槽位，未選中圖示以 inset 呈現 `24dp` 視覺尺寸。
- 選中文字使用 `14sp` 粗體，未選中文字使用 `12sp` 常規字重；重建、語言和主題切換後必須恢復正確選中項。
- 深淺色只切換 indicator、圖示和文字的語意色，不建立另一套導航幾何。

## 短文案排版

App 自有 UI 中的短標題、按鈕、text button、chips、短標籤、底部彈層標題、對話框標題和短操作項，應顯式使用穩定短文案排版策略。這些控件需要禁用字符間兩端對齊，保持 `letterSpacing=0`，並保留符合角色的 start、center 或 end 對齊，避免中文短文案在不同 Android 版本上被逐字拉滿到整個容器寬度。

Kotlin 動態建立的短文案控件應使用共用短文案 helper；XML 中的短按鈕、chips、標籤和標題應使用對應穩定 style 或等效顯式屬性。這個規則不得作為全局單行或固定高度策略，也不得覆蓋控件原本已有的省略、換行或觸控尺寸設計。

短文案規則不適用於長正文、路線站名、候選地點、用戶輸入、Citybus 或 DATA.GOV.HK 動態內容、路線詳情長段落、隱私或說明正文，以及由 Android 系統通知模板渲染的文本。這些內容應保留既有的換行、省略、對齊和可讀性策略。

## 主頁面

主頁面應該像一個高頻使用的查詢工具，第一屏直接提供行程選擇、查詢動作和路線結果狀態。

推薦結構：

```text
┌────────────────────────────┐
│ 巴士查詢          管理入口 │
├────────────────────────────┤
│ 常用行程選擇區域            │
│ 行程名稱                    │
│ 起點 -> 終點                │
├────────────────────────────┤
│ 查詢按鈕                    │
├────────────────────────────┤
│ 排序 / 查詢狀態 / 結果提示   │
├────────────────────────────┤
│ 路線結果卡片清單             │
└────────────────────────────┘
```

### 路線結果

查詢結果預設使用路線結果卡片，不再優先使用五清單格。

結果卡片的資訊優先級：

1. 路線號或路線組合
2. 候車時間
3. 價格
4. 總耗時
5. 步行距離

推薦卡片結構：

```text
┌────────────────────────────────────┐
│ 82X        約 4 分鐘        HK$ 6.5 │
│            總耗時 32 分鐘  步行 180米 │
└────────────────────────────────────┘
```

卡片字號建議：

- 路線號：20sp 到 24sp，粗體。
- 候車時間：18sp 到 20sp，核心狀態。
- 價格：15sp 到 16sp。
- 總耗時、步行距離：13sp 到 14sp。

結果清單一屏優先顯示 5 到 6 條完整結果。若與可讀字號衝突，優先保證字體舒適。

### 排序與狀態

- 常用與搜尋結果共用 checkable 排序按鈕 style，不應依賴難以發現的表頭點擊。
- 排序按鈕使用 `48dp` 最小高度、`14dp` 水平內距、`13sp` 文字和 `8dp` 相鄰間距；選中態以填充、文字對比和升降序箭頭共同表達。
- 排序總寬超出可用空間時使用水平滾動，不縮字或裁切字段文案。
- 查詢中應有明確但不阻塞的反饋，例如按鈕內進度、狀態條或結果區 loading placeholder。
- 查詢成功後結果卡片淡入或輕微上移進入。
- 查詢失敗和無結果應使用狀態卡或空狀態，不只顯示一行普通文本。

## 行程編輯頁

行程編輯頁應該像一個輕量表單，而不是後台配置頁。

- 頁面標題明確區分新增、編輯、複製。
- 行程名稱、起點、終點輸入框保持清晰的 helper text 或 hint。
- 起點和終點是一組關聯字段，視覺上應比普通上下排列更有關係感。
- 交換起點和終點使用圖示按鈕，不使用整行文字按鈕。

推薦交換控件結構：

```text
[ 起點輸入框                         ]  ↕
[ 終點輸入框                         ]
```

交換圖示要求：

- 使用彎曲雙向箭頭語義。
- 放在兩個輸入框右側中線附近，點擊區域不小於 48dp。
- 提供無障礙説明，例如“交換起點和終點”。
- 點擊後可使用 150ms 到 250ms 的旋轉或淡入反饋。
- 交換後仍執行原有地點選擇和儲存校驗。

地點搜尋要求：

- 搜尋 destination 使用左側連體起終點輸入欄和右側固定 `48dp` 交換操作區；候選開合不得令交換按鈕跳動。
- 起點候選插在起點與終點之間，終點候選插在終點下方；清單只與左側輸入欄同寬，同一時間只展開目前欄位。
- 搜尋頁最多展示 3 個完整候選，超出後由清單內部滾動；新增、編輯及複製行程頁繼續使用 3 至 6 項自適應策略。
- 起點目前位置操作與地點搜尋 loading 共用固定尾端工具槽，終點保留相同寬度，避免文字寬度隨狀態改變。
- helper、無結果、錯誤及 Google Maps attribution 緊跟實際所屬欄位；Google 地址交換至另一欄位時 attribution 必須跟隨，手動修改或選擇 Citybus 候選後清除。
- 搜尋加載反饋不阻塞輸入。
- 新輸入應取消舊搜尋反饋。
- 候選清單、無結果、失敗狀態要清楚區分。

### 搜尋結果操作

- 搜尋結果摘要同時提供次要「編輯」操作和較明顯的 tonal「儲存為常用行程」操作；保存的是目前起終點行程，不是某一條結果路線。
- 寬度小於 `600dp` 或 font scale 大於等於 `1.3` 時，摘要在上、操作列在下；寬度大於等於 `600dp` 且 font scale 小於 `1.3` 時可使用同列排列。
- 操作使用 `wrap_content + minHeight 48dp`，長英文和大字體以換行或縱向重排承載，不使用固定高度裁切。
- 首次沒有常用行程時保留靜態「路線結果預覽」，頁內只提供「新增常用行程」主操作；一次性查詢由底部「搜尋」Tab 承接。

## 行程管理頁

行程管理頁與主頁面保持同一風格，使用卡片清單表達已保存的行程配置。

推薦結構：

```text
行程管理                         新增
┌──────────────────────────────┐
│ 上學                           │
│ 漁灣邨 -> 北角衞理堂             │
│ 編輯   複製   刪除               │
└──────────────────────────────┘
```

- 新增行程應是頁面內明確主操作，可使用頂部按鈕或 FAB。
- 編輯、複製、刪除是卡片內次級操作。
- 刪除必須保留二次確認。
- 空狀態應提供新增入口，而不是隻提示「暫無行程」。

## 動效與反饋

動效目標是讓用戶感受到狀態變化，不是展示動畫本身。

推薦動效：

- 頁面進入：輕微 fade 或 slide。
- 查詢中：按鈕進度、狀態條或結果區 placeholder。
- 結果出現：清單整體淡入，卡片輕微錯峯進入。
- 排序切換：選中態變化和箭頭方向變化。
- 起終點交換：圖示輕微旋轉，兩個輸入框內容快速切換。

動效約束：

- 單個反饋通常控制在 150ms 到 300ms。
- 不阻塞輸入、滾動或頁面返回。
- 不做循環裝飾動畫。
- 不因為動畫導致佈局跳動。

## Android 實現取向

當前專案預設使用 XML + AppCompat + Material Components。後續 UI 改造優先沿用現有技術棧，避免為了單個頁面貿然引入 Compose。

可以考慮引入 Compose 的情況：

- 新頁面需要複雜狀態驅動佈局，XML 實現會明顯膨脹。
- 需要更復雜、可維護的轉場或清單動畫。
- 計劃逐步把多個頁面遷移到同一套 Compose UI 體系。

不建議引入 Compose 的情況：

- 只是調整字號、顏色、圓角、卡片和圖示按鈕。
- 只是重排現有表單或 RecyclerView 清單。
- 遷移會導致 XML 和 Compose 混用範圍過大，卻沒有清晰收益。

若 OpenSpec change 決定引入 Compose，需要在 `design.md` 説明原因、遷移範圍、與現有 XML 頁面如何共存，以及驗證方式。

## OpenSpec 使用約定

涉及頁面或互動的 OpenSpec change 應在 `design.md` 中引用本指南，並説明：

- 當前頁面使用的主風格是否為“安靜實用的現代通勤工具”。
- 是否採用結果卡片、狀態卡、圖示按鈕或輕量動效。
- 是否有偏離本指南的原因。
- 需要驗證的視覺目標，例如一屏顯示 5 到 6 條結果、核心字號是否舒適、觸控區域是否不小於 48dp。

涉及 UI 的 `tasks.md` 應包含至少一項視覺或互動驗證任務。Android 實現完成後，優先通過構建和真機或模擬器截圖確認關鍵頁面沒有文字重疊、佈局跳動或按鈕不可辨識的問題。
