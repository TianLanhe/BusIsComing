# BusIsComing UI／UX 風格指南

## 文件角色

本文件定義 BusIsComing 未來新增或改造界面時共同遵循的體驗方向、視覺語言、互動原則與設計決策方法。它不是目前畫面的逐頁說明，也不複製某個功能的完整 requirements、一次性改版方案或驗收記錄。

- 本文件回答「新的 UI／UX 應以什麼原則設計，以及遇到取捨時如何判斷」。
- 生效 OpenSpec 回答「目前某個功能對使用者可觀察的精確行為是什麼」。
- [本地化指南](localization-guidelines.md)負責三語、術語、動態資料與 TTS；[驗收矩陣](localization-validation-matrix.md)負責語言、主題、尺寸、字體及無障礙覆蓋。
- 現有頁面與元件可以作為正例，但不能因「目前就是這樣」取代設計理由。若新需求需要偏離本指南，應在對應 OpenSpec `design.md` 說明原因、影響範圍與驗證方式。

本指南中的「應」與「不得」是長期規則；帶有「例如」的內容只用來解釋原則，不把當前頁面結構永久凍結。

## 體驗定位

BusIsComing 是「安靜、實用、可信賴的現代通勤工具」。使用者通常在時間有限、注意力分散或正在移動的情況下操作，因此界面應幫助使用者快速判斷目前行程、下一步操作和巴士狀態，而不是要求仔細研究畫面。

### 核心體驗

- **一眼可判斷**：最重要的行程、路線、候車狀態和主操作先被看到，次要資料不與其競爭。
- **最短可預期路徑**：高頻任務步驟少、入口穩定；相同動作在不同頁面保持相同語義與回饋。
- **狀態真實可信**：清楚區分載入、成功、空、部分成功、過期及失敗，不以假資料或模糊文案製造已成功的印象。
- **上下文連續**：刷新、編輯、語言／主題切換和生命週期重建盡量保留仍有效的內容、位置與選擇，不讓使用者重做無關操作。
- **平靜克制**：色彩、卡片和動效用於建立層級及解釋變化，不用營銷式 hero、裝飾光斑、無意義插圖或持續動畫搶奪注意力。
- **所有人都可完成**：三語、小屏、大字體、深色模式、TalkBack、鍵盤及不同輸入方式從設計開始即納入，不在完成後補救。

### 取捨順序

設計目標衝突時，依序保障：安全與真實狀態、任務可完成性、無障礙與三語、上下文連續、一致性、資訊密度，最後才是裝飾效果。不得為了單屏多放一項、追求視覺對稱或保留動畫而犧牲文字完整、觸控、恢復路徑或狀態可信度。

## 設計原則

### 資訊層級先於容器

- 每個畫面或狀態先確定一項主要資訊和一項主要操作，再安排輔助資訊、次級操作及補充說明。
- 以字級、字重、位置、留白和語意色建立層級；不要只靠增加卡片、邊框或背景色分組。
- 同一層級的內容保持相同視覺權重。不能把全部資訊都加粗、著色或放入高對比容器。
- 通勤資料優先表達「它是什麼、現在如何、可以做什麼」。例如路線卡先讓人辨認路線和候車狀態，票價、耗時、步行及詳情依重要性逐級展開。

### 一個狀態有清楚的主操作

- 一個畫面或明確任務區域原則上只有一個最高權重 action；其他操作使用描邊、文字、圖示或 overflow 降級。
- 相同權重的按鈕不應因文案長短、載入狀態或資料出現而交換位置。不可用 action 應說明前置條件；不能只降低透明度而讓原因不可理解。
- 熟悉且低風險的操作可以使用圖示；不熟悉、破壞性或容易混淆的操作應同時提供文字、可訪問名稱或確認。
- 可立即復原的操作優先提供撤銷；刪除全部資料、取代匯入等難以復原的操作需要明確確認及結果摘要。

### 漸進披露，避免首屏過載

- 首屏保留完成當前任務所需的資訊；長說明、完整站序、多班 ETA、進階設定等內容按需進入詳情、展開區或 Bottom Sheet。
- 不為「看起來功能很多」同時展示所有控制。低頻操作可以放入次級頁或更多選單，但不得因此變得無法發現。
- 摘要被省略時，使用者必須有穩定入口取得完整內容；`contentDescription` 亦應保留必要語義。

### 穩定幾何與上下文

- loading、helper、錯誤、選中態或動態資料切換不應令核心 action 跳動、列表失去錨點或使用者正在操作的控件消失。
- 刷新與局部補全優先保留可用內容，在原位置表達正在更新；只有提交了會改變結果語義的新請求時，才按功能契約清除舊內容。
- 同一手勢同一時間只有一個明確 owner。內外層滾動、下拉刷新、候選列表、Bottom Sheet 與 AppBar 不應在邊界意外接管同一手勢。
- 重建、返回、主題或語言切換後，仍有效的 destination、輸入、選擇、排序和閱讀位置應可恢復。

### 失敗時仍可理解與恢復

- 外部服務局部失敗時，已取得且仍可信的內容繼續可用；失敗的部分獨立降級，不用整頁錯誤覆蓋全部結果。
- 錯誤回饋說明「哪一部分未完成、目前還能做什麼、如何重試或離開」，不向一般使用者暴露 provider 狀態碼、exception 或內部術語。
- 任何自動化行為都應有可見結果和停止／恢復路徑；不在背景靜默改寫使用者輸入、選擇或持久資料。

## 視覺語言

### 色彩與主題

- 深青綠是品牌主色，用於核心操作、選中狀態及候車重點；琥珀色只用於次級但需要明確操作感的入口。危險、錯誤和停用狀態使用各自語意色，不借用品牌色混淆語義。
- layout、drawable 及 Kotlin 動態 View 使用 `bus_*` 語意色 token，不直接寫固定白／黑、日間 surface 或僅在一種主題成立的顏色。
- 頁面背景可沿用低對比 `bus_page_gradient_*`，表單可沿用 `bus_form_gradient_*`；漸變只建立柔和空間層次，不成為視覺焦點。
- 深色模式不是把淺色反相或改成純黑。文字、surface、divider、outline、error、selected、disabled、status bar、navigation bar、Dialog 與 Bottom Sheet 都使用對應夜間語意 token。
- 主要文字對比至少 4.5:1，必要圖示與邊界至少 3:1。選中、錯誤、警告、停用及排序方向不能只靠顏色區分。
- launcher、品牌圖像及路線識別色可以固定，但前景與標籤必須在淺深主題均可辨認。

### 文字層級

- 文字角色至少區分頁面／Dialog 標題、區段標題、核心動態資料、正文、輔助資料、標籤及 action。新頁面優先複用既有 text appearance，不為單一畫面建立近似但不同的字級。
- 核心動態資料可以使用較大字級或較高字重；輔助資料降低權重但仍需可讀。字重和顏色不應同時過度放大同一層級。
- App 自有短標題、按鈕、chip、短標籤及操作項使用 `StableShortText*` 或等效策略：`letterSpacing=0` 並明確設定 alignment，避免中文在部分 Android 版本被逐字拉滿。
- 短文案策略不適用於正文、使用者輸入、站名、地點候選、路線詳情或第三方動態內容；這些內容應自然換行，不能為維持單行而縮字。
- 使用者行程名與站名可在緊湊摘要中受控省略，但詳情、分享或無障礙描述應能取得完整內容。

### 間距、密度與對齊

- 以 4dp 節奏組織尺寸，常用間距優先取 8、12、16、24dp；具體值依內容關係和現有共用資源選擇，不要求所有頁面套用同一組固定間距。
- 關係越緊密的元素距離越近；區段之間的留白應明顯大於同一區段內部間距。不要用多條 divider 補救分組不清。
- 文字、圖示和 action 沿可理解的基線或邊界對齊。動態文字長度改變時，核心操作槽位與主要對齊線保持穩定。
- 資訊密度服務於快速掃讀，但不得以固定高度、縮字、裁切 action 或顯示半個列表項換取更多內容。

### 表面、形狀與圖示

- 卡片用於承載一個可獨立理解、選擇或操作的資料對象；普通分組優先使用留白、標題或 divider，避免 card 套 card。
- surface、輕描邊和克制陰影只表達層級。一般卡片沿用接近既有 8dp 的克制圓角，Dialog 等浮層可使用較大圓角；膠囊只用於 chip、狀態、選中 indicator 等具有明確語義的元素。
- 優先使用與 Material 語義一致、全 App 已採用的圖示。圖示風格、筆畫與視覺尺寸保持一致，不混入裝飾性 emoji 或來源不明的圖形。
- 圖示的視覺尺寸可以小於觸控區，但核心 action 的觸控目標至少 48×48dp。

## 導覽與互動架構

### 選擇承載層級

- 頂層 destination 只承載高頻、彼此獨立且需要保留狀態的主要任務；不能為單一設定、一次 action 或短流程隨意增加頂層入口。
- 次級頁適合需要獨立標題、返回語義、較長內容或多步操作的任務。
- Dialog 適合短決策、確認或少量設定；Bottom Sheet 適合不離開上下文的詳情與操作。內容在小屏或大字體下無法完整到達時，應改用可滾動浮層或次級頁。
- 導覽的選中狀態必須持續可見；ripple 只表示按下，不能代替目前位置。返回後應回到合理的來源與狀態，而不是一律重置首頁。

目前「常用／搜尋／設定」及其精確幾何屬於已實現的產品契約，見生效的 [`app-chrome-layout`](../openspec/specs/app-chrome-layout/spec.md) 等 OpenSpec；它是上述原則的一個實例，不是未來所有導航都必須複製的模板。

### 輸入與搜尋

- label 說明欄位用途，hint 只提供格式或例子，不能讓已輸入內容覆蓋後失去欄位語義。
- 校驗、搜尋中、無結果、錯誤、定位及 attribution 緊跟所屬欄位，狀態解除後清除；沒有動態狀態時不預留空 helper 行。
- 具有關係的輸入應形成一個可理解的組，例如起點與終點。交換、清除、定位和 loading 等尾端 action 使用穩定槽位，避免狀態切換造成跳動。
- 搜尋不阻塞持續輸入；新 query 使舊 callback 失效。候選、IME action、按鈕與下拉刷新不能因同一次意圖重複提交。
- 鍵盤顯示時，輸入、候選和主 action 仍應可達；導航、內容與 IME 的幾何由共用 WindowInsets 策略及生效產品契約處理，不在單一頁面用視窗平移、固定高度或 magic number 臨時修補。

### 狀態與回饋

每個新畫面或可獨立刷新的區域都應設計適用的狀態，而不是只畫成功畫面：

| 狀態 | 表達原則 |
| --- | --- |
| 初始 | 說明可執行的下一步；沒有資料時提供與任務相符的入口 |
| 載入 | 保留必要上下文，提供不阻塞的進度；避免無限期無文字 spinner |
| 成功 | 突出主要資訊和下一步，避免成功提示遮住結果 |
| 空 | 區分「尚未建立」「條件下沒有結果」和「資料被清除」，提供合適操作 |
| 部分成功 | 展示已取得內容，局部標明仍在補全或無法取得的部分 |
| 刷新／過期 | 保留舊內容並標明更新狀態或時間，不把過期資料冒充最新 |
| 失敗 | 說明影響、可重試範圍和其他可行路徑 |
| 停用 | 保留 action 語義並讓前置條件可理解 |

- 欄位問題使用 inline 回饋；短暫且可恢復的操作結果可用 Snackbar；需要持續閱讀或操作的狀態留在內容區；只有阻塞決策才使用 Dialog。重要失敗不得只靠 Toast。
- 狀態更新應可被 TalkBack 感知，但不要讓高頻 ETA 或 loading 變化反覆搶奪焦點。
- 同一狀態在不同頁面使用一致的圖示、色彩、標題和 action 層級；文案按具體原因調整，不能用一個「發生錯誤」覆蓋所有情況。

## 共用元件模式

新界面先判斷能否複用既有模式，再決定新增元件。複用的是資訊結構、狀態和互動語義，不是把某頁 layout 整段複製到另一頁。

| 模式 | 適用情況 | 長期要求 |
| --- | --- | --- |
| 資料卡片 | 行程、路線等可獨立理解或選擇的對象 | 一個主要識別、一個主要狀態；次要資料分層，不塞入全部詳情 |
| 設定／導覽列 | 重複的設定入口、目前值或次級頁入口 | 整列語義清楚，主文與摘要自然換行；不把不相關 action 塞入同一列或 Dialog |
| 狀態卡 | 查詢、刷新或外部服務狀態 | 只描述所屬任務區域，不無故取代仍有效的輸入或內容 |
| 輸入組 | 具有共同提交或互相影響的欄位 | label、動態回饋、尾端工具及手勢 owner 明確，錯誤定位到具體欄位 |
| Dialog | 短確認、短設定或不可逆操作提示 | 標題、內容、主次 action 清楚；小屏與大字體下全部可達 |
| Bottom Sheet | 需要保留來源上下文的詳情或操作 | 支持完整滾動、返回與焦點恢復；內容過重時升級為次級頁 |

既有 `StableShortText*`、`RouteResultSortButton`、`SettingsRow`、查詢狀態卡及語意色 token 是目前共用實現入口。精確頁面行為以生效 OpenSpec 為準，例如路線結果見 [`route-query-results-layout`](../openspec/specs/route-query-results-layout/spec.md)，地點輸入見 [`route-place-selection`](../openspec/specs/route-place-selection/spec.md)；不要在本指南再次複製全部 scenario。

## 適配、本地化與無障礙

- 約 360dp portrait 是核心小屏基準，不是固定畫布。較大螢幕應改善留白和可讀寬度，不只是把元素拉伸；不得用大屏驗證替代小屏問題。
- layout 使用內容寬度、最小尺寸、weight、constraint、換行或滾動適配三語和 font scale 2.0。核心文案與 action 不縮字、不裁切；必要時由一列重排為多列。
- 核心 action 觸控目標至少 48×48dp，焦點順序符合視覺與任務順序。圖示 action、選中狀態、錯誤、排序方向及動態狀態提供可訪問名稱和非顏色線索。
- TalkBack 描述提供完成任務需要的完整語義，不逐字重複畫面，也不把裝飾元素加入焦點順序。操作完成、失敗或重要狀態變化應有適度公告並恢復合理焦點。
- status bar、navigation bar、IME、手勢導航和三按鍵導航不能遮擋必要內容或 action。系統 inset 由共用策略處理，不在每頁加入彼此衝突的 magic number。
- App 自有文案遵守香港繁體、獨立審校簡體及自然英文；第三方動態文字、使用者名稱和術語邊界遵守[本地化指南](localization-guidelines.md)。具體設備與狀態組合按[驗收矩陣](localization-validation-matrix.md)執行。

## 動效原則

動效只用來回應操作、解釋狀態或維持空間關係：

- 按下、選中、交換、展開、收合及內容替換可以使用 fade、slide、scale 或圖示變化；一般單次反饋約 150–300ms。
- 動效開始前後的資訊層級與最終幾何必須清楚，不因 animation 造成 action 跳位、列表錨點丟失或重複點擊。
- 重要結果不等待裝飾動畫才可讀；長列表不做大範圍錯峰進場，不使用循環脈衝、漂浮或背景裝飾動畫營造「活躍感」。
- 系統停用或降低動畫時，直接套用終態，所有流程仍可理解、可操作。

## 實現與演進

- 目前 UI 基線是 XML、AppCompat、Material Components、RecyclerView 與 SwipeRefreshLayout。新界面優先複用現有 theme、style、drawable、formatter、WindowInsets 及共用元件，不在 Activity／Fragment 複製顏色、尺寸和狀態判斷。
- 同一視覺或互動規則在多處使用時，沉澱成語意 token、style、drawable、共用 View／controller 或可測 policy；不要只把數值抄到本文件後繼續在 layout 硬編碼。
- 文件描述角色與使用原則，資源和共用元件保存精確實現值，OpenSpec 保存使用者可觀察契約。三者不一致時先查明是實現遺漏、設計變更還是文件漂移。
- 引入新的 UI 技術棧、全新導航模型或與本指南不同的視覺系統屬於架構決策，必須在 OpenSpec `design.md` 說明收益、共存邊界、遷移成本及驗證，不為單一頁面臨時引入。

## 新 UI／UX 決策清單

新增頁面、元件或重要狀態前，至少回答：

1. 使用者在什麼情境進入，最想完成什麼？這是高頻、低頻、緊急還是不可逆任務？
2. 第一眼必須看到哪一項資訊？目前狀態的唯一主 action 是什麼？
3. 應使用頂層 destination、次級頁、Dialog、Bottom Sheet 還是現有頁面的 inline 區域？退出及返回後保留什麼？
4. 初始、載入、成功、空、部分成功、刷新／過期、失敗、停用如何表達和恢復？
5. 可以複用哪些語意色、text appearance、間距、元件、formatter 和互動 policy？新增模式是否真的會跨場景使用？
